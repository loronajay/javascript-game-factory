# Speed Demon — Campaign Plan (scope)

The rivals are a catalog with a difficulty order and no fiction around them.
This is the plan to hang a career on them. It is a scope document: `GDD.md`
records intent, `CLAUDE.md` records what is built, this records what is agreed
and not yet started.

**Scoped out, deliberately:** per-car performance specs. Cars stay
cosmetic-only. Difficulty is looser hands and different *race formats*, never a
faster car — the rule the rival roster already follows. Also out: open world,
dialogue trees, an economy, police, new driving mechanics.

---

## The one decision everything else follows from

**A campaign race is a rival race with a script around it.** Not a new race, not
a new screen, not a new opponent system.

`SCREEN_RACE` already carries three different things — a coach, an online
session, a rival playhead — and stays one implementation of driving. Campaign is
the fourth. `init-game.js` gains a `campaignRun` alongside `coachedRun` and
`rivalCar`; the race itself is built by the same `raceOptionsFor` +
`buildRival` path the Rival Race mode uses today.

Three consequences worth protecting:

- **The opponent is `buildRival`, unchanged.** A campaign rival is still an
  input log generated by `driveRace` before the tree goes green, so it is bound
  by the player's own physics and cannot be handed an advantage. Everything
  downstream — playback, drawing, deciding who won — keeps one path.
- **`sim/` learns nothing about the campaign.** No event ids, no chapter, no
  progression. `race.js` already refuses to know what mode it is in; that does
  not change.
- **An event is data.** No `if (rivalId === "knox")` anywhere. Campaign design
  becomes authoring, which is the property `MODES`, `RIVALS` and the various
  `*-catalog` modules already have.

## What already exists and is being reused as-is

| Need | Already built |
|---|---|
| An AI opponent with human failings | `rival/cpu-driver.js` — five knobs, seeded, triangular jitter |
| Ten drivers with faces and profiles | `rival/rivals.js` |
| Turning a driver into a raceable log | `rival/lineup.js` → `buildRival` |
| Deciding who won, and saying so | `rivalOutcome`, `rivalSummary` |
| Best-of-N, red lights, per-round grace | `sim/match.js` — pure and import-free |
| Distances and clocks as objectives | `sim/modes.js` → `raceOptionsFor` |
| A screen that is the race screen plus something | the coach / online / rival pattern |
| Local-first store with a server seam | `records/records-store.js`, `rival/ghost-store.js` |

Nothing in this plan requires a change to `scripts/sim/`. That matters beyond
tidiness: `sim/` is mirrored into `factory-network-server` and both repos replay
a committed golden fixture, so a campaign that stays out of `sim/` cannot break
online.

```
  formats.js      PURE. the race formats, and how each decides a result

```

The pure/impure split is the cabinet's fourth-going-on-fifth instance of the
same rule (radio, garage, online, records). `tests/modules.test.js` should sweep
`campaign/` the same way: only `progress-store.js` may name `localStorage`,
`window.`, `fetch(`.

### An event row

```js
{
  id: "ch1-vee-1",
  chapter: 1,
  rivalId: "vee",              // must be an id in RIVALS
  format: FORMAT_DUEL,
  title: "First Impressions",
  splash: "street-race.png",   // assets/mission-splashes/
  trackId: "track-a",
  objectiveId: "quarter",      // an option id the format's mode actually offers
  seed: 4117,                  // reproducible rival behaviour
  profileOverride: { reactionSeconds: 0.5 },   // optional: this rival, tonight
  requires: [],                // event ids
  unlocks: ["ch1-wizard-1"],
}
```

**`profileOverride` is how a rival returns stronger** without a second rival
row and without a faster car. Vee in chapter 1 and Vee in chapter 3 are the same
person with tighter hands. It merges over `RIVALS[].profile` through
`createProfile`, which already normalizes.

**`seed` is authored per event**, so a given event plays the same way every
time it is attempted. That is the deterministic architecture the cabinet already
depends on, and it makes an event's difficulty assertable in a test rather than
eyeballed.

## Race formats

Formats are where variety comes from now that car specs are out of scope. Each
is a row in `formats.js` naming the mode it builds on and the rule that decides
the result. All of them run the existing race.

| Format | Builds on | Result rule |
|---|---|---|
| `duel` | rival race | first across the line |
| `grudge` | rival race | best of 3 via `sim/match.js` |
| `holeshot` | rival race, eighth mile | first across — launch and 1–2 decide it |
| `top-end` | rival race, half or mile | first across — gearing and the late shifts decide it |
| `ghost-time` | distance race, rival's log as a ghost | beat a fixed time set by the rival |
| `clean-run` | rival race | win **and** no shift graded below `good` |
| `survivor` | time attack | cover a distance the rival's log reached |

**A clean-run requirement is a constraint, not an objective.** `createRace`
throws unless exactly one objective is named, and that stays true — the
constraint is evaluated after the fact by reading `race.shifts`, in
`formats.js`, where the campaign lives. Do not add a third objective kind for
it.

**`ghost-time` and `survivor` need no second car on screen** if that reads
better — the rival's log gives a number, and the player races the number. Worth
one of the seven events in the first chapter just to prove the format table
isn't only cosmetic.

## Progression and save

```js
{
  version: 1,
  completed: { "ch1-vee-1": { wins: 1, losses: 2, bestMs: 12482, at: 1770000000000 } },
  unlocked: ["ch1-vee-1", "ch1-wizard-1"],
}
```

**Campaign progress works signed out**, and this is the records rule rather than
the garage rule. The distinction is already settled in `CLAUDE.md`: a garage
requires an account because a livery only means something if an opponent can see
it; a personal record works locally because it is meaningful to the player
alone. A career is the second kind. Local is the whole truth signed out and the
fast path signed in.

**The local copy is keyed by player id**, like the garage cache, so a shared
browser cannot show one account another's career.

**Server sync is deferred and additive.** `game_progress` exists, but its public
*claim* path runs every claim through `validateTacticalArenaPublicClaim` and
rejects any non-TA slug. That blocks *entitlements*, which the campaign does not
grant — nothing here unlocks a car, because every car is already free. So sync,
when it comes, is a plain progress write and does not need that refactor first.

**A campaign race still files to the distance boards.** It is a rival race, and
a rival race is physically identical to a solo one over the same distance —
`recordsAs` on the mode row already says so. A campaign win that also sets a
personal best is the loop working, not a leak. `ghost-time` and `survivor` file
the same way as their underlying mode.

## Screens

```
title ──▶ CAMPAIGN ──▶ hub ──▶ bio ──▶ splash ──▶ race ──▶ campaign result ──▶ hub
                        └────────────────────────────────────────────────────┘
```

`SCREEN_CAMPAIGN` (the hub), `SCREEN_RIVAL_BIO`, `SCREEN_CAMPAIGN_RESULT`. The
race is `SCREEN_RACE`, unchanged.

- **Campaign is a fourth title-menu item**, above START. It has one way in and
  so needs no remembered return — the `SCREEN_COLLECTION` / `SCREEN_BOARDS`
  rule, not the radio's.
- **Every screen owning a cursor belongs to exactly one input path** in
  `init-game.js`, and to the debug handle's `move()` dispatch.
  `tests/shell.test.js` and `tests/modules.test.js` already assert both; three
  new screens is three new assertions, not three new rules.
- **The splash is a beat, not a screen** if it can be — a held panel over the
  staged race, dismissed with ENTER, exactly as a coaching hold works. Worth
  trying that first; it costs no screen and no cursor.
- **The campaign result card reuses the results panel.** `rivalSummary` already
  replaces the headline caption with the verdict; a campaign adds the unlock
  line under it. The panel is sized to clear `DASH_TOP` and cannot grow
  downward, so anything new rides on the existing `sub` line or replaces it.

### The bio screen

This is the payoff for the art that already exists.

- `assets/characters/<first>-<last>-<nickname>.png` — the ten full-scene
  portraits, finally drawn at a size worth their resolution.
- `assets/characters/character-bios.txt` — ten written bios, currently prose in
  a text file. These want to become a `blurb`-style field on the campaign side
  rather than parsed at runtime; `rivals.js` already carries a one-line `blurb`
  and an `accent`, and the long bio belongs beside the campaign because it is
  fiction rather than a race parameter.
- `assets/mission-splashes/rivals-and-bosses/<id>.png` — a per-rival splash for
  all ten, matching the `RIVALS` ids exactly.

**Two asset notes to settle before building:**

1. **The bios call Cole Mercer "Torque"; the roster, the portrait filename and
   the splash all say "Wizard".** Ids are never renamed — a rival id is
   authored into events, saves and ghosts — so if the name changes it changes
   as `name`, and `id: "wizard"` stays. Pick one and make the bio text agree.
2. **The portraits are ~22MB for ten files** and all ten load at boot for 56px
   cells. The hub and bio screens make the originals genuinely useful, which
   flips the existing note: keep the masters for the bio screen, and add a
   downscaled set (256×256, ~40KB each) for the rival pane and hub list.

## The chapters

Ten rivals, four chapters, ~26 events. Order follows the measured difficulty
ladder (Vee 15.34s → Kuroda 12.37s over a quarter), and rivals recur with
tightened `profileOverride`s rather than disappearing.

**Chapter 1 — The Street.** Vee, Switch, Saint. Duels and one holeshot. Teaches
the loop.
**Chapter 2 — Making a Name.** Knox, Mako. Grudges, a top-end run, rematches
against chapter 1 at a tighter profile.
**Chapter 3 — The Circuit.** Mirage, Wizard, Prince. Ghost-time and clean-run
appear. Mirage gets the mile, per his bio.
**Chapter 4 — Kuroda.** Zero, then Kuroda. Best-of-five, clean-run finale.

The bios already suggest formats: Mirage is long highway runs, Knox is launches,
Zero keeps records of every run, Mako punishes one mistake. Match the format to
the fiction — that is free characterisation.

## First milestone

Build the spine on **one chapter of three events** before authoring the other
twenty-three.

1. `campaign/events.js`, `chapters.js`, `formats.js` — catalog only, three
   events, three formats (`duel`, `grudge`, `holeshot`).
2. `campaign/progress.js` + `progress-store.js`, local only.
3. `ui/campaign.js` + `render/campaign.js` — hub and bio.
4. Shell wiring: title item, three screens, input paths, debug handle.
5. `campaignRun` in `init-game.js`, building on `buildRival`.
6. Tests: format result rules, progression/unlock, the module purity sweep, the
   shell's one-path-per-screen assertion, and a measured difficulty assertion
   per event the way `tests/rival.test.js` measures the ladder.

If those work, chapters 2–4 are authoring. If they don't, three events is what
was spent finding out.

## Open, not decided

- **Does losing block progress, or just not unlock?** A career that hard-gates on
  a rival somebody cannot beat is a wall. Leaning toward: an event can be
  retried freely, and a *chapter* advances on a win count rather than on every
  event.
- **Does the campaign get its own boards?** Leaning no, for the reason rival
  races don't: it would split one ladder.
- **Reputation as a number.** In the original sketch and not obviously earning
  its place while nothing can be bought with it. Unlocks are doing the work.
