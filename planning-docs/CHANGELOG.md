## Speed Demon Personal Bests + the Platform's Second Rating Source (2026-08-08)

Speed Demon's results screen used to show you a time and nothing to beat. It now keeps personal bests, submits them to a global board, and places one of them on the cross-game ladder rail — which meant teaching the platform that a ladder can be built on something other than head-to-head ELO.

**A board is a mode and an objective, and both exclusions were measured rather than assumed.** Seven boards: four distances, three clocks. Not per track, because `ui/track-layout.js` keeps the painted road geometry in one shared `ROAD` and only the dash rhythm and scenery differ — the five tracks are the same road in five settings, so splitting them would be five boards competing for one time. Not per car, because the roster is cosmetic-only and every model performs identically, so per-car boards would be 24 copies of one ladder. Both are still recorded per row as display metadata. If stat differences ever land, the board id gains a class segment and every existing id keeps meaning what it meant.

**The second rating source.** `services/ladder-catalog.mts` had anticipated this in a comment since it was written — "when a second source appears, add its `source` value here and give `db/ladders.mts` a branch for it — do not fork the registry" — and that is exactly what happened. `game_run_records` (migration 036) sits alongside `game_ratings` (018) rather than inside it: an ELO row is a running total that moves both ways, a record row is a high-water mark that only improves, and one table holding both would mean one of them lying about what its number means. The two sources are merged in JS rather than UNIONed, because a union would reconcile two orderings and two meanings of "rating" inside one statement to produce a ranking that is re-sorted afterwards anyway.

Only the quarter mile is registered on the rail. Registering all seven would bury every other cabinet's ladder under one game; the full set is served by `/leaderboards/speed-demon`, which the cabinet reads directly. A run-records placement is shaped identically to an ELO one — W/L/D zeroed, since a solo board has no opponent — so the profile rail renders it without knowing which it got, and `formatLadderRating` delegates to the board because a quarter mile best is `11924` in the column and `11.924s` on screen.

**Bests work signed out, and that is the deliberate opposite of the garage.** A garage requires an account because a livery only means something if an opponent can see it — a paint living in one browser cannot be shown to anybody. A lap time is the reverse: meaningful to the player alone. So signed out the cabinet keeps bests locally and says `SIGN IN TO RANK IT` rather than pretending to be offline, and signing in adds the board on top. The consequence is that the local copy is not merely a cache: `load` merges **per board** rather than letting either side win, since the server can be behind on a run set offline and the local copy can be behind on one set from another machine. Signed-out bests live under a fixed key and are never donated to whoever signs in next — two people sharing a machine is indistinguishable from one person signing in on their own laptop.

**A submitted time is a claim, and it is stored as one.** This is the part that matters for a *global* board, where the alternative is believing whatever a console call reports. Three steps, and only the third is a guarantee: the catalog refuses values outside the board's plausibility bounds (the impossible, not the suspicious — a 3-second quarter mile, not a fast one); the run is stored `verified: false` with its input log alongside; and a later pass replays that log through the deterministic sim to settle the flag. **The third step is deliberately not built.** Keeping the log now is what makes it possible at all — retrofitting verification later would mean discarding every record already set. An implausible value is refused rather than clamped, because clamping would *store* the forgery.

Speed Demon was unusually well placed for this: `sim/input-log.js` and a deterministic sim already existed, because `factory-network-server` replays both drivers' logs to adjudicate online races. The gap was that the log was recorded for online runs only, so `recordThrottle` moved out of `tickOnline` to the one point both paths reach on the way to `stepRace`, with `raceTick` incrementing beside it — that pairing (exactly one tick per `stepRace` call) is the invariant `replayRun` mirrors.

**Ranked 1v1 is prepared, not built,** and the survey is written down in the cabinet's `CLAUDE.md` so it does not have to be redone. `ranked_queue`/`ranked_matches` are already keyed on `game_slug` and `db/ranked-elo.mts` is pure and names no game, so the whole brokering stack is reusable; the only accidental coupling is two Tactical Arena-shaped columns (`board`, `ban_first`) that a second game has to make nullable first. The rating slug is `speed-demon-ranked`, following sumorai, which keeps casual play off the ladder — and it will have to join the list `POST /ratings/:slug` refuses by name, or a client could invent a session against the public ladder. The open question is adjudication: `factory-network-server` already knows who won but has no database and no way to tell `platform-api`, and there is no service-to-service auth on `platform-api` today. Either two-sided client attestation (the Tactical Arena pattern, no new trust boundary) or a shared secret (stronger, but a second authentication surface). Not decided.

Three live bugs fell out of the client tests, all one root cause: `Number(null)` is 0, and **0 is a legal value on a time-attack board** — a run that never moved covered no distance. So an unset field coerced through `Number` read as a real, achievable result. It gave a record to a race that never finished, kept malformed saved rows alive through normalization, and printed "no best yet" as `0.000s`.

597 API tests (+22), 1063 cabinet tests (+38). Browser-verified end to end: a run files, a faster run reports its delta, an equal run does not, and a guided practice run records nothing — the coach stops the world, so its clock bears no relation to a driven one.

## Founder Friendship + Announcement Broadcast (2026-08-04)

Two "the platform greets you" features, both of which are really about one thing: a new account should not land on an empty arcade.

**The founder friendship.** Every new sign-up is befriended with the account behind `FOUNDER_EMAIL` — the Tom pattern. It is a real friendship through `createFriendshipBetweenPlayers`, not a special-cased row: symmetric, ledgered, worth the standard +100 friend points, syncing the `friends` column and `player_metrics` on both sides, and removable by either party like any other. A second concept of "friend" that only this feature understood would have to be taught to every surface that reads the friends rail.

Two properties are deliberate and worth not undoing. It is **opt-in by configuration** — `FOUNDER_EMAIL` is its own variable, never derived from `ADMIN_EMAILS`, because granting someone operator authority must not also make them everyone's first friend; unset means the feature does nothing and does not even spend a database round trip finding that out. And it is **best-effort** — a missing founder account, a database hiccup, anything, and registration still succeeds. Someone who just handed over an email and a password has to end up with an account; a cosmetic friendship is not worth failing that over. `services/founder.mts` returns a reason string for every failure mode and throws for none of them.

It is awaited rather than fired and forgotten: the client goes straight to the profile after registering, and a friendship landing a second later would show an empty rail on the very first page load — the one load this feature exists to fix.

**Announcement broadcast.** Publishing a bulletin or adding an event now notifies every registered account — `bulletin_posted` (summary as the preview, link to the board) and `event_posted` (deep link to `/event/?slug=`, since events have their own page). These are the only two writes in the platform addressed to everyone at once, so they share one implementation, `services/content-announce.mts`, differing only in a small per-kind config.

The once-only guarantee lives in SQL rather than application logic. Migrations `033`/`034` add `announced_at` to both tables, and the claim is a conditional `update ... where announced_at is null and <visible> returning id`. Two concurrent publishes cannot both win — Postgres serializes the update and the loser matches no rows. An operator fixing a typo on live content re-notifies nobody, because the claim has been spent.

The fan-out is one statement — `insert into notifications ... select from accounts` — with deterministic per-row ids (`notif-<kind>-<id>-<playerId>`) and `on conflict (id) do nothing`, so a retried broadcast lands on the same rows instead of giving everyone a second copy. The kind is *in* the prefix because both id spaces are uuids from the same generator; without it, a bulletin and an event that happened to share an id would silently swallow each other's announcement. The publishing operator is excluded from their own blast.

**What counts as visible differs, and that's the interesting part.** A bulletin has a draft state, so `published` + `public` is the gate and the operator has a natural staging area. An event has no draft — the calendar hides only `cancelled` — so a `scheduled` event is public the instant it is created, and *creating* it is what notifies. The gate is `scheduled` or `live`: `completed` is excluded because announcing a past event tells everyone about something they can no longer attend, and that exclusion makes `cancelled` usable as the staging state, since it never spends the claim. Create quietly as cancelled, flip to scheduled, and the flip is what goes out. This is documented in the admin guide, because it is the one place the two flows genuinely behave differently.

Announcing is a side effect of the save, never a precondition for it: the service swallows its own failures, the route wraps the call anyway, and the audit entry records `notified` and `recipientCount` so the Audit tab can answer "did that actually go out?" after the fact. A `friends` or `private` bulletin never broadcasts — the fan-out has no audience filter, and pretending otherwise would leak content past its own audience. Deleting either kind clears its notifications through `deleteNotificationsByPayloadRef` (`contentId` added to the allowlist), so no alert outlives what it points at.

Both headlines lead with the announcement (*📢 New bulletin: Tournament Night*, *🗓️ New event: Sactown Smackdown X*) rather than with the poster. Every account receives them; "Jay posted a bulletin" reads as a social action when it is a noticeboard notice.

## Bulletin Attachments (2026-08-04)

Bulletins can carry one image — the immediate need was a tournament flyer for Sactown Smackdown X. Migration `032-bulletin-image.sql` adds `bulletins.image_url`, mirroring `012-thought-image.sql`: a plain URL column with an empty-string default, not a join to `player_photos`, because a bulletin image belongs to the announcement rather than to anyone's gallery.

Upload reuses the existing `/upload/photo` endpoint rather than adding an admin-only one — it already validates by magic bytes instead of the client's declared MIME type, and caps the long edge at 1200px with `crop: "limit"`, so a portrait poster is scaled whole instead of cropped.

**Posters letterbox, they don't crop.** Both the board card and the console preview constrain the image by max-width *and* max-height and let the frame size to its content, so a 2:3 flyer isn't stranded in a wide black band and a landscape banner still fills the card. Cropping a flyer to a landscape strip would cut the date, venue, and entry fees off the bottom — the exact information the announcement exists to carry. Same no-destructive-crop rule the profile backgrounds follow.

`httpUrl` in `db/content-shared.mts` restricts the column to http(s), with the same guard repeated in the browser normalizer — the value lands in an `<img src>` on a public page, and the column is writable through the admin API.

One non-obvious fix: the console re-renders the whole panel when an upload completes, which would have silently wiped a half-typed announcement. `state.bulletinDraft` captures the form before the re-render. Edit-vs-create mode still reads the *stored record*, not the merged draft — a draft on an unsaved bulletin is truthy but has no id, which would otherwise offer Delete on nothing.

## Admin Console (2026-08-03)

The platform gained an operator. Until now every route in `platform-api` authorized the same way — *is the caller the owner of this row?* — which is right for player data and cannot express "the person who runs the arcade". Bulletins and events were frozen arrays compiled into the browser bundle (`DEFAULT_BULLETINS`, `DEFAULT_EVENTS`), so publishing an announcement meant editing TypeScript and redeploying. There was no moderation beyond self-deletion of your own comments.

**Authority is a column, not a token.** Migration `031-admin-console.sql` adds `accounts.is_admin`, and `db/admin.mts#isAdminPlayer` is re-read on *every* admin request rather than trusted from a JWT claim — tokens live 30 days, and a revoked admin has to lose access on their next call. `ADMIN_EMAILS` on Railway promotes matching accounts at boot; it can grant but never revoke, so a typo in an env var cannot strip authority from a live operator. `/auth/me` reports `isAdmin` purely so the nav can show an Admin link; nothing server-side trusts it. Demoting the last admin is refused inside a transaction, because there would be no way to grant the flag back.

**One gate, one place.** `routes/admin-routes.mts` matches the whole `/admin/` prefix, checks authentication then authority, and only then delegates to `admin-content-routes.mts` and `admin-moderation-routes.mts` — neither of which contains any authorization logic. A new admin endpoint added to either is gated by construction. Every state-changing action writes to `admin_audit_log`; the audit-coverage test walks all twelve mutating routes and asserts each one logs exactly one attributable entry.

**Admin deletes are separate functions, not a flag.** `db/thoughts.mts` and `db/photos.mts` bind ownership into the delete predicate itself. Threading an `asAdmin` escape hatch through them would put the ordinary player's ownership guarantee one mistaken argument away from being skipped, so `db/moderation.mts` holds ownership-free deletes reachable only from the gated route. The player-facing paths were not touched.

**The stability contract for cabinets.** `cabinet_overrides` rows only change how the *grid presents* a cabinet — `games/<slug>/game.json` stays the authority for what a game is. `applyCabinetOverrides` in `arcade-catalog.mts` is the only place admin data touches the grid, and it will not change `href`, `slug`, or `previewImage`, will not add a cabinet the catalog does not already have, and treats every null field as "inherit". Deleting a row restores the shipped presentation exactly. `js/tests/admin-catalog-overrides.test.mjs` pins all of it, including that a hostile row cannot repoint a card.

**Null vs empty is load-bearing.** `content-api.mts` returns `null` when the platform could not be asked and an array when it answered. Only `null` falls back to the shipped fixtures; `[]` renders an empty board. Without that distinction an operator who unpublishes everything would watch demo content reappear with no way to clear it. A backend outage degrades the public pages to exactly the pre-console site.

**Suspensions are time-boxed.** A suspended account keeps read access — which is what makes the notice visible — but every non-GET outside `/auth/` is refused, games included. Suspending an admin is refused in the SQL predicate so the console cannot be locked.

Also shipped: a player-facing **Report** control on thought cards (`data-report-id`), without which the moderation queue could never receive anything. It sits in the same slot as Delete and is mutually exclusive with it. `POST /reports` takes the reporter from the verified session, never the body, and dedupes repeat filings through a partial unique index.

Console lives at `/admin/` (`js/admin-page/`: entry / state / actions / two renderers / shared helpers), seven tabs, hash-routed so a tab survives a reload. 512 API tests, 66 shared-frontend tests, 19 profile-social tests — all green.

## Test-Suite Repairs (2026-07-30)

Verifying the documentation pass above surfaced three broken or misleading test setups. All three are fixed; every cabinet suite in the repo is now green.

**Creature Battler was silently untested.** All eight of its test files are CommonJS, but there was no `package.json` under `games/creature-battle/`, so they inherited `"type": "module"` from the repo root and every one died at load with `ReferenceError: require is not defined in ES module scope` — nothing executed, under either `node <file>` or `node --test`. Adding `games/creature-battle/package.json` with `"type": "commonjs"` and a `test` script fixed the load. That is safe because the cabinet's own `scripts/*.js` are classic browser scripts with no `import`/`export`, and `js/mobile-controller.mjs` stays ESM on its extension.

Once they actually ran, four years-stale expectations surfaced — worth recording, because each one is a trap the next person will hit. The tests load game code by reading it with `fs` and evaluating it in a `vm` sandbox stubbed with hand-written collaborators, so **a new cross-file call in game code fails as a `ReferenceError`, not a meaningful assertion.** `battle-round.js` had grown calls to `accumulateBattleStats`, the end-of-round status/passive tickers, and `CreatureState.clearDefend`; `battle-engine.js` had grown the whole passive/skill-registry surface. Both needed new stubs. Sound-path expectations lacked the `creature-battler/` prefix that the outer platform entry point requires. And `SPD DOWN` labels are now stat-stage deltas (`SPD -1`) under the ±5-stage system.

The subtlest one: stubbing `getWarlordPresenceBonus` to `0` made **every** damage number collapse to `1`. Despite the name it is a multiplier (1.0 inactive, 1.08 active) folded into `calcDamage`'s `passiveMult`, so a zero silently floors damage to `ENGINE.MIN_DAMAGE` and presents as "the engine is broken" rather than "the stub is wrong". Stub multipliers as `1`.

**Battleshits' `npm test` ran eight of eleven suites.** The script chains files by name and omitted `audio`, `bot`, and `emojis` — all passing, all unguarded by the default command, including the entire bot AI. Added, along with focused `test:bot` / `test:audio` / `test:emojis` entries. The name-by-name style means a new test file still has to be registered by hand or it never runs.

**Mini-Tactics' failing main-menu test was the test's fault, not the product's.** `tests/main-menu.test.js` asserted a "Tutorials" button on the main menu; removing that button was a deliberate owner decision. The assertion was inverted to pin the button's *absence*, keeping the checks that the tutorial completion screen stays wired. `mainMenuScreen.js` already bound `startTutorial` optionally (`?.addEventListener`), so the menu works either way, and the tutorial subsystem remains intact behind the scenes. 143/143.

## Factory Launcher — Custom Domain + Progress-Sync Repair (2026-07-27)

**The site moved to `factory.jayarcade.com`.** The apex `jayarcade.com` belongs to the separate `loronajay/games-directory` repo (Jay's Retro Arcade and the Cabinet OS the Pi kiosks pull from) and must not be reassigned — GitHub allows one repo per domain. A subdomain avoids that entirely: one Namecheap CNAME (`factory` → `loronajay.github.io`), a `CNAME` file at the repo root, Enforce HTTPS on (Let's Encrypt cert issued 2026-07-28 01:18 UTC). The custom domain serves the repo at the **root**, not under `/javascript-game-factory/`; all in-site paths are relative so nothing broke, and GitHub redirects the old Pages URLs. `APP_BASE_URL` on Railway and the CORS allow-list in `platform-api/src/http-utils.mts` both moved with it (the old Pages origin stays allow-listed for old links). The privacy page's contact became `leojaylorona@gmail.com` — no mailbox exists on the domain.

Two operational gotchas found the hard way: saving the custom domain in Settings → Pages makes GitHub commit a `CNAME` straight to `main`, so the next local `git push` is rejected until you `git pull --rebase` (never force-push it — that unsets the domain); and Railway's GitHub connection had silently broken ("GitHub Repo not found"), so backend pushes were deploying nothing. Auto-deploy from `main` with root directory `platform-api` is reconnected.

**Progress sync: signed-in accounts could end up with progress the server never had.** The one-time local-ownership migration (`migration:local-ownership-v1`) could be *consumed without granting anything* — a fresh device (a new packaged-app install signing into an existing account) posted an empty backfill, which burned the one-shot for the whole account. The device that actually held the progress could then never migrate it, so the server owned nothing and every other surface correctly showed zero. Fixed in three places: an empty backfill is inert server-side, the client no longer posts one, and accounts already stranded self-heal while the server owns nothing for them. Verified end-to-end on a real device — units, skins, Valor, tutorials, and campaign clears all landed on the Android build from the server. Trust model and the follow-up to close the widened window: `games/tactical-arena/SECURITY.md`.

Debugging note worth keeping: Chromium batches localStorage writes into leveldb, so `adb`-pulled dumps of the packaged app are stale unless you `am force-stop` the app first. Several dumps during this investigation looked like the sync had never run when it had.

A hardening pass closed the money-critical holes. ## Factory Launcher — Top Ladder Rankings (2026-07-25)

The "Top Ladder Rankings" panel on `/me` and `/player` had a normalize contract and a renderer but nothing behind it — both pages passed `ladderPlacements: []` forever. It now shows real cross-game standings.

The data was already there and already game-agnostic: `game_ratings (player_id, game_slug, rating, wins, losses, draws)` is written by `POST /ratings/:slug` (no slug allowlist) and by the ranked match reporter. What was missing was a platform-level read — the only leaderboard query lived inside the auth-gated `/ranked` family and folded in Tactical Arena's ranked cosmetics.

**The plug-in point is `platform-api/src/services/ladder-catalog.mts`.** Adding a game's ladder is one entry (`gameSlug`, `title`, `cabinetSlug`, `source`, `unitLabel`, `minMatches`) — the placement query, the public board route, `GET /ladders`, and both profile panels all read the registry, so which games rank is a data question, never a code question. The rating slug is deliberately separate from the cabinet slug: Sumorai stores ranked play under `sumorai-ranked` so casual matches never touch the ladder, and `title` lives in the registry because such a slug has no catalog entry to derive a name from. Registered today: `tactical-arena`, `sumorai-ranked`.

`db/ladders.mts` holds the two reads. `getPlayerLadderPlacements` ranks a player across every registered ladder in one query (window `rank()` per `game_slug`, joined against an `unnest` of the registry's slugs and per-ladder placement thresholds) and returns rank, field size, rating, and record. `getLadderStandings` is the public top-N board for one ladder. Both share one ordering — rating desc, win differential, then `player_id` — which makes the order total, so a board row and that player's profile placement can never disagree. Migration `025` adds the matching `game_ratings (game_slug, rating desc, …)` index; the primary key is `(player_id, game_slug)` and would have sorted the whole table per request.

`routes/ladder-routes.mts` serves `GET /ladders`, `GET /ladders/:gameSlug`, and `GET /players/:playerId/ladders`, all public — standings are public information, and the auth gate on `/ranked` exists because those routes also queue and report matches. The handler is dispatched **before** the `/players` family so the `ladders` suffix is not swallowed; a route-order test pins that, since a regression there would silently empty the rail rather than error.

Client-side, placements are fetched live (`fetchPlayerLadderPlacements`) by `me-page/page-data` and `player-page/loader`, never cached: a standing moves whenever anyone *else* on that ladder finishes a match, so a stored copy is stale by definition. `buildRankingItems` prefers live placements over whatever sits on the profile record and renders a fuller line — `1284 ELO` over `Rank #3 of 42 · 12W-4L-1D` — trimming to just `Rank #N` when a source carries nothing more. Empty states now say a placement has to be earned instead of promising standings are "coming online".

Still open: badges keyed off placement (`planning-docs/badge-plans/…` defers these pending ranked seasons and placement history), and a public board page — `GET /ladders/:slug` has no UI outside Tactical Arena's own in-game modal yet.

## Factory Launcher — Comment Moderation (2026-07-25)

Players can now delete comments on their own posts and photos, so moderation of a thread doesn't require deleting the whole post. The rule is the same on both surfaces: a comment can be removed by **its author** or by **the author of the post / owner of the photo**.

Backend owns the decision. `deleteThoughtComment` (`db/thoughts.mts`) and `deletePhotoComment` (`db/photos.mts`) load the comment and its parent inside a transaction, check the requester against both stored owner ids, delete, then recount and write back `comment_count`; they return `{ ok, reason }` so the routes can map `forbidden` → 403 and `not_found` → 404. `DELETE /thoughts/:id/comments/:commentId` and `DELETE /photos/:id/comments/:commentId` take the requester from the **verified session** (`authClaims.playerId`), never from the request body — `handleThoughtRoute` now receives `authClaims` for this reason (it previously took none).

**Every thought mutation is now account-holders-only, with the actor taken from the verified session.** `POST /thoughts`, `/thoughts/:id/comments`, `/shares`, and `/reactions` previously had no auth at all and read the actor from the request body — so any caller could post, comment, share, or react *as anyone*. All four now require a session and derive the actor from it; `POST /thoughts` also overwrites any body-supplied `authorPlayerId`. The photo comment/reaction routes already required a session but still read `actorPlayerId` from the body, letting any signed-in user act as another player; they now use the session id too.

The frontend had to follow, because `/thoughts` and `/player` are public-read pages whose social actions gated on the *local factory profile* — which every guest has. Both pages now resolve the auth session at boot and treat guests as read-only (`/me` already redirects to sign-in, so it was unaffected). Reading stayed public on purpose: opening a comment thread no longer requires a profile, and the sheet renders the thread for everyone but swaps the reply form for a "Sign in to join the conversation." prompt when signed out — the same shape the photo viewer already used for its comment form.

`DELETE /thoughts/:id` gained authorization in the same pass. It previously took an id and deleted, with no auth check at all — any caller who could reach the API could delete anyone's post. It now requires a verified session and only lets the post's author delete it. `deleteThought(db, thoughtId, requesterPlayerId)` carries the ownership check inside the delete statement (`where id = $1 and author_player_id = $2 returning id`) rather than doing a read-then-delete, so concurrent requests cannot race past it; when nothing is deleted it does a follow-up existence check purely to answer 404 vs 403. The response body is unchanged (`{ deleted, id }`), and the local-first client ignores the API result before deleting from its own cache, so guest posts (local-only, never persisted) still delete normally.

Deleting social content now also clears the notifications that announced it. Notifications embed a snapshot of what they reference, so a removed comment/post/photo used to leave a notification pointing at nothing. `deleteNotificationsByPayloadRef` (`db/notifications.mts`) deletes by `payload->>'<key>'`, with the key allowlisted to `commentId`/`thoughtId`/`photoId` since it is interpolated into a jsonb lookup; it swallows its own errors so cleanup can never fail the content deletion. Wired into four routes: comment delete (both surfaces) clears by `commentId`, post delete clears by `thoughtId`, photo delete clears by `photoId` — the last two only when the delete reports something was actually removed. No client change was needed: the notification badge and list refresh on page load and on each dropdown open, so a cleared notification simply stops appearing.

Frontend mirrors the rule only to decide whether the control is worth showing. `renderCommentSheet` reads `commentPanelState.viewerPlayerId` plus the new `commentTargetAuthorPlayerId` card field (for a repost, the *original* author — moderation follows the thread, not the card) and `buildCommentListHtml` reads `viewerPlayerId`/`isPhotoOwner`. The photo viewer gained `isPhotoOwner` alongside the existing `isOwner`: `isOwner` gates that surface's own "Remove Photo" button, `isPhotoOwner` is the identity fact, which is what the profile-embedded viewer needed (it offers comment moderation but not photo removal). Local-first `deleteThoughtCommentPost` mirrors the same rule for guests; `deleteThoughtCommentWithApi` only touches the local cache after the server confirms.
